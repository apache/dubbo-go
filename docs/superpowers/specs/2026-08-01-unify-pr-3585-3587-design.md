## 生产行为设计

### 新生成项目的 `make test`

#3585 合入后的 fresh scaffold 不包含生成的 PB/Triple 源码，但模板中的 `test` target 只运行 `go test ./...`。因此用户在刚执行 `newApp` 或 `newDemo` 后直接运行 `make test` 会在协议源码尚未生成时失败。

两个模板统一改为：

```makefile
test: proto-gen tidy
	go test ./...
```

对应修改：

- `tools/dubbogo-cli/generator/application/makefile.go`
- `tools/dubbogo-cli/generator/sample/makefile.go`
- `tools/dubbogo-cli/cmd/testGenCode/template/newApp/Makefile`
- `tools/dubbogo-cli/cmd/testGenCode/template/newDemo/Makefile`

这使 `make test` 成为生成项目的完整可执行入口，同时保持 `proto-gen`、`tidy` 和 `test` 仍可独立调用。

### 模板依赖版本

`v3.3.1` 是当前已发布的稳定版本；`v3.3.1-20260727` 是指向旧 develop 基线的日期标签。面向新用户的模板统一使用：

```text
dubbo.apache.org/dubbo-go/v3 v3.3.1
```

Go 版本继续使用 #3585 设定的 `go 1.25`，与当前仓库 Makefile 的 `GOTOOLCHAIN=go1.25.0+auto` 一致。

### EOF 处理

application 和 demo server 模板中的双向流循环使用：

```go
if errors.Is(err, io.EOF) {
	return nil
}
```

这样能同时处理直接的 `io.EOF` 和被底层包装的 EOF。需要同步 generator 源和 golden template。

## 测试设计

### TDD 红灯

在修改模板 Makefile 前，先增加一个 Linux E2E 测试：

1. 使用真实 `application.Generate` 或 `sample.Generate` 写入 `t.TempDir()`。
2. 在 fresh scaffold 中执行 `make test`。
3. 捕获完整输出，失败时包含项目类型和命令输出。

在当前 develop 行为上，该测试应因为 fresh scaffold 尚未生成 PB/Triple 源码而失败。必须保存该失败输出，确认失败原因不是工具缺失或网络问题。

随后只修改模板 Makefile 的依赖关系，使同一测试通过。

### 普通单元回归

保留或重写以下检查：

- `TestNewApp` 和 `TestNewDemo`：generator 输出与 golden template 完全一致。
- 旧 logger import 扫描：检查 generator 和 golden template 中的 Go 文件。
- 模板依赖版本检查：生成后的 `go.mod` 必须包含稳定 `v3.3.1`，且不得包含日期预发布版本。
- EOF 模板检查通过真实生成文件与 golden 比较覆盖，不单独复制生产逻辑到测试 helper。

### E2E 测试的本地门禁

需要 `protoc` 和两个插件的测试通过环境变量显式启用：

```text
DUBBOGO_CLI_E2E=1
```

未设置时测试 `Skip`，普通 `go test ./...` 不强迫所有开发者预装协议工具链。CI 必须显式设置该变量并提供工具链，所以 CI 不会跳过该测试。

`tools/dubbogo-cli/Makefile` 增加固定 target：

```makefile
test-generated-projects:
	DUBBOGO_CLI_E2E=1 go test ./cmd -run TestGeneratedProjectsCompile -count=1
```

### CI 工具链

在 Linux CI 中增加独立步骤：

1. 安装 `protobuf-compiler`。
2. 安装与模板一致的 `protoc-gen-go` 版本。
3. 从当前仓库的 `tools/protoc-gen-go-triple` 模块安装本地生成器。
4. 确认 `protoc`、`protoc-gen-go`、`protoc-gen-go-triple` 都可从 `PATH` 发现。
5. 执行 `make -C tools/dubbogo-cli test-generated-projects`。

不得仅依据进程退出码；测试输出必须显示 `newApp` 和 `newDemo` 两个子测试均执行。

## 风险与回滚

- CI 安装协议工具链会增加时长；通过独立 E2E step 隔离，不增加普通开发者单测前置条件。
- 生成项目依赖稳定 `v3.3.1`，而 Triple 插件来自当前 develop；E2E 测试负责证明这组版本真实兼容。
- 网络或依赖下载失败必须归为环境问题，不得通过跳过测试或降低断言绕过。
- 合并冲突解决后若发现 #3585 的完整设计与稳定 `v3.3.1` 不兼容，停止实现并报告具体编译证据，不恢复内嵌生成文件作为临时绕过。
- push 后若 GitHub Head 与本地不一致，不进行 force-push；保留本地 commit，重新获取并合并远端变化。
