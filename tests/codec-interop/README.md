# Triple compatibility and Java interoperability

From the repository root, run `./tests/codec-interop/run.sh` to exercise three real integration checks. The script also resolves the repository root from its own path, so it can be invoked by path from another directory.

1. A client pinned to dubbo-go `v3.3.2` calls the current checkout's Hessian2 Triple server, then the current checkout's client calls a separately built `v3.3.2` server. Both calls assert the returned greeting. This checks compatibility across separately built Go versions rather than using the current implementation's legacy API in-process.
2. The Apache `dubbo-go-samples` non-Protobuf Triple sample runs its Go/Java client-server interoperability matrix at pinned commit `6e791058f58fd28434f859eb132eb93dd26d5418`. It covers Go client to Go server, Go client to Java server, Java client to Go server, and Java client to Java server. The script checks the expected greeting from each direction instead of relying on process exit codes alone. The Java sample pins Dubbo `3.3.0-beta.3`.

The script requires Go, Java, Maven, Git, and network access, and requires TCP port `20000` to be free. It builds in a temporary directory, replaces only the sample's dubbo-go module with this checkout, and removes the temporary files and server process on exit. To use an already-cloned sample repository without another network clone, set `DUBBO_GO_SAMPLES_DIR` to a checkout at the pinned commit; the script copies committed files into its temporary directory and leaves that checkout untouched. The legacy client lives in a nested module intentionally: the main module cannot import a second version of dubbo-go under the same module path. Root `go test ./...` does not execute this integration test; invoke the script explicitly.
